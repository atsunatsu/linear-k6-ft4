# 真实 0.3q 中 `command 0x35` 处理路径分析

## 这份文档回答什么问题
这份文档只回答当前最关键的一个问题：

- `DigiManager` 发给电台的 `command 0x35` 到底是什么
- 真实 `0.3q` 固件里是否存在与这类帧对应的处理路径
- 当前最应该继续追的是哪一段固件代码

它**不**直接回答这些问题：

- 空口上现在发出来的 `FT4` 是否已经合格
- 是否已经可以停止修改 `DigiManager`
- 是否已经证明所有问题都只在固件里

## 当前结论
当前最可信的结论是：

1. `DigiManager` 发给固件的不是音频流，而是 `command 0x35` 私有数字控制帧。
2. 当前 replay 里的业务包平均只有 `8~9` 个非零字节，更像**稀疏控制帧**，不像完整音调序列。
3. 真实 `0.3q` 固件里能直接找到和 `DigiManager` 完全一致的：
   - 4 字节帧头常量 `STXBUFF`
   - 4 字节帧尾常量 `ETXBUFF`
   - 与公开 `uart.c` 相同的 16 字节扰码表
4. 真实固件里能看到 `FT8 / APRS / WSPR / SCAN / RECV / AUTO` 这组模式字符串，但当前仍然看不到 `FT4` 字样。
5. 把 Thumb 反汇编地址基准修正后，之前怀疑的 `0x32 / 0x33` 邻近分发表**重新变成了可复验真证据**：
   - `0x0d90 cmp r0, #0x32`
   - `0x0dfc cmp r0, #0x33`
6. 但当前仍然没有直接看到 `cmp ..., #0x35`。
7. 因此更合理的理解不是“固件里没有命令分发”，而是：
   - `0x32 / 0x33` 这类命令属于一条可见的上层分发链
   - `0x35` 更像进入了**第二级解释器**，或被归到更大的数字模式命令家族里处理

## DigiManager 侧已经确认的事实
当前已经确认 `DigiManager` 的主下发路径是：

- `UDPDataCheck`
- `SetDigitalData2`
- `SetCECMessage2(command 0x35)`

当前最可信的 `command 0x35` 布局是：

1. `bytes[0..3] = STXBUFF`
2. `byte[4] = command id`
3. `bytes[5..6] = payload length (little endian)`
4. `bytes[7..11] = 5-byte sender header`
5. `bytes[12..15] = ETXBUFF`
6. `bytes[16..] = forwarded payload bytes`

这说明 `DigiManager` 输出给固件的是一种**私有数字控制帧**，不是普通 CAT 改频命令，也不是声卡音频。

## replay 为什么说明它更像控制帧
当前 `FT4` 与 `FT8` replay 的业务包统计都很稳定：

- 平均非零字节数约 `8.7`
- 热点主要集中在：
  - `0..2`
  - `244..247`
  - `254..255`

这类分布更像：

- 固定头字段
- 少量尾字段
- 少量模式/控制参数

而不像：

- 完整音调序列
- 完整调制样本流

所以当前更合理的理解是：

> `DigiManager` 更像是在把 `FT4/FT8` 上游数据压成“控制 + 参数帧”，再交给固件。

## 真实 0.3q 固件里已经找到的同协议家族证据
### 1. 同源帧头、帧尾、扰码表
当前已经确认真实固件里存在：

- `STXBUFF`：`0xDEA4`
- `ETXBUFF`：`0xDEA8`
- 16 字节扰码表：`0xDB10`

这很重要，因为它说明：

- 真实 `0.3q` 并不是和公开 CEC 协议完全无关的另一套实现
- 它更像是**同一家族协议的另一层解析器**

### 2. `0xDE94` 常量簇
在 `0xDE94` 附近存在一个很值得继续追的混合常量簇：

- 前半段是指向 `FM / CT / DCS / DCR` 的字符串指针
- 后半段紧接：
  - `STXBUFF`
  - `ETXBUFF`
  - 一组数字参数

这更像：

- 模式描述表
- 协议参数表
- 或第二阶段 parser 的常量簇

而不像随机堆在一起的无关数据。

## 新证据：`0x32 / 0x33` 的邻近分发表是真的
把反汇编地址基准修正到正确的 Thumb 地址后，固件里出现了可复验的代码窗口：

```text
0x0d90 cmp r0, #0x32
0x0d92 beq ...
...
0x0dfc cmp r0, #0x33
0x0dfe bne ...
```

这说明：

- 固件里确实存在一条**按命令号分发**的可见路径
- 之前把这块完全降级为“假阳性”是过度保守了

但同样要注意：

- 这依然**不是** `0x35` 的直接证据
- 当前更像是：`0x35` 不走这条最浅层分发，或者要在更深一层才被识别

## 字符串指针表的新证据
除了常量簇之外，固件里还找到了多张**表驱动字符串表**。当前最明确的是：

- `0xD778` 开始的一张 8 字节步长表
- 表项形式像：
  - `string pointer`
  - `small tag / id`

这张表里能看到：

- `NONE`
- `FLASH LIGHT`
- `POWER`
- `MONITOR`
- `SCAN`
- `VOX`
- `LOCK KEYPAD`
- `SWITCH VFO`

这说明真实固件至少有一部分 UI / 模式逻辑是**表驱动状态机**。

这条证据很重要，因为它支持当前主判断：

> `command 0x35` 很可能不是简单硬编码 case，而是进入某种表驱动的第二级解释路径。

## 当前最应该继续追的方向
当前最值得继续追的，不是回头怀疑 `WSJT-X`，也不是只盯 `DigiManager`，而是：

1. 沿着 `0x0d90 ~ 0x0e1e` 这段 `0x32 / 0x33` 分发表继续往下看
   - 弄清这条分发链到底属于哪一类控制命令
   - 看它是否和数字模式状态变量共享上下文
2. 继续追 `0xDE94 ~ 0xDEBC` 常量簇的真实代码引用
3. 继续找和数字模式字符串 `FT8 / APRS / WSPR` 相关的表驱动入口
4. 把“字符串指针表 -> literal pool -> 真实代码入口”这条链补完整

## 当前不该做什么
当前不建议：

- 再把 `WSJT-X` 上游当成主嫌疑对象
- 再把 `0x32 / 0x33` 彻底当成假阳性扔掉
- 在没有更多固件证据前，就断言慢节拍全由 `DigiManager` 单独造成

## 对协作者的建议
如果你是后续接手这个项目的人，当前请这样理解：

- `WSJT-X` 上游给出的 `FT4` 数据大概率没问题
- `DigiManager` 负责把上游数据压成 `command 0x35` 控制帧
- 真实固件里已经能证明：
  - 有同协议家族常量
  - 有可见命令分发路径
  - 有表驱动字符串结构
- 但 `0x35` 的真正处理点还没直接钉死

所以主线应该是：

> 继续定向逆向真实 `0.3q` 固件里 `command 0x35` 的第二级解释路径，而不是再回到泛泛的全镜像盲扫。
