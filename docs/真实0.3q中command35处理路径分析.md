# 真实 0.3q 中 `command 0x35` 处理路径分析

## 这份文档回答什么问题
这份文档只回答当前最关键的一个问题：

- `DigiManager` 送给电台的 `command 0x35` 到底是什么帧
- 真实 `0.3q` 固件里是否存在与这类帧对应的处理路径
- 如果暂时还没直接看到 `cmp ..., #0x35`，那下一步该往哪里继续追

它**不**回答这些问题：

- 空口上现在发出来的 `FT4` 是否已经合格
- 是否已经可以停止修 `DigiManager`
- 是否已经确认固件就是唯一责任方

## 当前结论
当前最可信的结论是：

1. `WSJT-X -> DigiManager` 上游给出的 `FT4` 数据本身没有问题。
2. `DigiManager` 送给固件的不是音频流，而是 `command 0x35` 私有数字控制帧。
3. 这些业务包平均只有 `8~9` 个非零字节，更像**稀疏控制帧**，不像完整音调序列。
4. 真实 `0.3q` 固件里可以直接找到和 DigiManager 完全一致的 `STX/ETX` 常量，以及和公开 `uart.c` 相同的 16 字节扰码表。
5. 真实固件里已经能看到 `0x32`、`0x33` 的候选分发块，但还没有直接看到字面比较 `0x35` 的处理点。
6. 固件里能直接看到 `FT8 / APRS / WSPR / SCAN / RECV / AUTO` 这组模式字符串，但看不到 `FT4` 字样。
7. 在 `0xDE94` 附近还能看到一个混合常量簇，前半段是 `FM / CT / DCS / DCR` 字符串指针，后半段紧接 DigiManager 同源的 `STX / ETX` 和一组数字参数。
8. 因此更合理的理解不是“固件里没有 `0x35`”，而是：

   **`0x35` 更像进入了第二层解释器，或被归入更上层命令家族处理。**

## DigiManager 侧已经确认的事实
当前已经确认 DigiManager 的主下发路径是：

- `UDPDataCheck`
- `SetDigitalData2`
- `SetCECMessage2(command 0x35)`

其中：

- `protocol 8` 会走 `SetDigitalData2`
- `SetDigitalData2` 会组一个 5 字节 sender 头
- `SetCECMessage2` 会组完整帧并写给电台

### `command 0x35` 当前最可信的布局

1. `bytes[0..3] = STXBUFF`
2. `byte[4] = command id`
3. `bytes[5..6] = payload length (little endian)`
4. `bytes[7..11] = 5-byte sender header`
5. `bytes[12..15] = ETXBUFF`
6. `bytes[16..] = forwarded payload bytes`

### 已确认的帧头帧尾
DigiManager 构造函数里实际初始化的值是：

- `STXBUFF = [0x59, 0x57, 0x58, 0x73]`
- `ETXBUFF = [0x95, 0x75, 0x85, 0x37]`

## replay 为什么说明它更像控制帧
当前 `ft4-replay.json` 和 `ft8-replay.json` 的业务包统计很稳定：

- `FT4` 业务包平均非零字节数约 `8.7`
- `FT8` 业务包平均非零字节数约 `8.7`

热点位置主要集中在：

- `0..2`
- `244..247`
- `254..255`

这类分布更像：

- 固定头字段
- 少量尾字段
- 少量模式/控制参数

而不像：

- 完整音调序列
- 完整调制样本流

所以当前更合理的理解是：

> DigiManager 更像是在把 `FT4/FT8` 业务数据压成“控制 + 参数帧”，再交给固件。

## 真实 0.3q 固件里已经能看到什么

### 1. 同协议家族常量确实存在
在真实 `cec_0.3QB.packed.bin` 解包后的固件里，已经直接命中：

- `STXBUFF`：`0xdea4`
- `ETXBUFF`：`0xdea8`
- 公开 `uart.c` 相同的 16 字节扰码表：`0xdb10`

这件事很重要，因为它说明：

- 真实固件并不是和公开 CEC 协议完全无关的另一套系统
- 它更像是**同一协议家族的另一种帧格式/另一层解析器**

### 2. 固件里有 FT8 类数字模式字符串，但没有 FT4
在真实固件里已经能直接看到：

- `FT8`
- `APRS`
- `WSPR`
- `SCAN`
- `RECV`
- `AUTO`

但当前还没有直接找到 `FT4` 字样。

这不等于“固件绝对不支持 FT4”，但它意味着：

- 固件公开知道 `FT8` 这一路
- `FT4` 更可能不是一条独立公开命名路径
- 它更可能是被挤进现有数字发送链，或依赖更隐蔽的解释分支

### 3. 当前还没有直接看到 `cmp ..., #0x35`
到目前为止，我们还没有在真实固件里直接命中明确的：

- `cmp r?, #0x35`

但已经命中了：

- `cmp r0, #0x32`
- `cmp r0, #0x33`

而且这些比较出现在相邻分发块里。

这说明：

- 固件里确实存在“按单字节命令值分发”的路径
- 但 `0x35` 不一定直接走这条最外层分发

### 4. `0x32/0x33` 那段不能再被草率当成最终答案
之前我们一度把 `0x32/0x33` 附近那块看成“非常像 `0x35` 也会走进去的命令分发器”。

现在看，这个判断要收紧：

- 那一块**确实值得继续追**
- 但它未必就是 `0x35` 的直接入口
- 更可能是 `0x35` 先经过一层 frame parser，再进入更深层状态处理

也就是说：

> `0x32/0x33` 依然是好锚点，但不能再把它直接等同于“找到 0x35 了”。

### 5. `0xDE94` 附近更像模式描述表，不像随机常量
把 `0xDE94` 附近按 32 位值去看，会看到：

- `0xeaab -> "FM"`
- `0xece3 -> "CT"`
- `0xece6 -> "DCS"`
- `0xecea -> "DCR"`

紧跟在这些字符串指针后面的，就是：

- DigiManager 同源的 `STXBUFF`
- DigiManager 同源的 `ETXBUFF`
- 一串还未完全解释的数字参数

这说明 `0xDEA0` 一带更像：

- 模式描述表
- 协议参数簇
- 或第二阶段 parser 使用的常量簇

而不是几组偶然拼在一起的无关常量。

## 这对当前研发方向意味着什么
这轮分析把主线再收紧了一步：

1. 继续修 `DigiManager` 是对的，因为 sender 确实会把上游差异压平。
2. 但不能再简单假设“慢节拍一定完全由 DigiManager 本机定时造成”。
3. 现在必须同步认真追：
   - `DigiManager -> command 0x35`
   - 真实 `0.3q` 固件里如何解释这类 frame`

更直白一点说：

- `WSJT-X` 上游问题已经基本排除
- `DigiManager` 不是完整本机调制器，更像组包器 + 写出器
- 真实固件对 `0x35` 的第二阶段解释路径，已经变成主线问题

## 当前最值得继续做的事
下一步最值钱的工作不是回头怀疑 `WSJT-X`，而是：

1. 继续修 DigiManager 的发送组织方式
2. 同时沿真实固件里的：
   - `0x32 / 0x33` 邻近分发块
   - `0xDE94 ~ 0xDEBC` 常量簇
   - 同协议家族扰码 / 帧头 / 帧尾
   去追 `0x35` 的第二阶段 parser

## 协作者应该如何理解当前状态
如果你是后面接手这个项目的人，当前请这样理解：

- 不要再把 `command 0x35` 当成“肯定能直接搜到的简单 case 值”
- 不要再把 DigiManager 单纯看成“本机完整调制器”
- 当前真正该追的是：
  - `SetDigitalData2 -> SetCECMessage2(0x35)` 的 sender 语义
  - 真实 `0.3q` 固件里 `0x35` 的第二阶段解释路径
