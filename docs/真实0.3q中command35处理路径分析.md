## 2026-05-26 新增进展：`0x35` 更像进入“有界状态机”

这轮继续沿着 `0x0DBE -> 0x0280` 往下看，又拿到一条比之前更硬的证据：

- `0x0DBE` 会把 `u8(r2)` 送进 `0x0280`
- `0x0280` 不是普通 helper，而是一个 **LR 相对字节跳表**
- 其中子码 `0x35` 会跳到 `0x02EA`
- `0x02EA` 最终只产出：
  - `out_a = 0`
  - `out_b = 3`

随后 `0x0DCC ~ 0x0DF4` 这段会：

1. 读取 `0x20000094`
2. 把它夹在 `out_a/out_b` 这个很小的范围里
3. 再和 `r4` 组合后写回
4. 另外还会用 `0x7FFFFFFF` 作为上界哨兵值

目前在 dispatcher 邻域里，已经能稳定识别出这些运行时状态引用：

- `0x20000094`：反复读写，最像“当前子状态 / 当前 profile / 当前索引”
- `0x20000740`：更像 guard 或上下文块
- `0x7FFFFFFF`：更像饱和或边界哨兵

因此当前判断需要再收紧一步：

> 现在盯住的 `0x0DBE -> 0x0280 -> 0x20000094`，更像上层的模式/参数状态机，  
> 而不像真正把 FT8/FT4 变成空口节拍的最终数字发送器。

这对主线的意义是：

- 不能把这段代码直接当成“FT4/FT8 最终发射 parser”
- 但它很可能仍然是进入真正数字发送路径前必须经过的一层分类器
- 后续逆向应该继续回答：
  - 这个状态机之后谁真正接手数字发送
  - `0x20000094` 到底代表哪类模式/子状态
  - 谁最终把这些子状态转成 FT8/FT4 的空口节拍
