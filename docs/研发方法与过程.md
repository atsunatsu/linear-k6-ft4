# 研发方法与过程

## 这份文档给谁看
这份文档是给**参与这个项目研发的人**看的，不是给普通测试者看的。  
它的目的不是教你怎么刷机，而是告诉你：

- 这个项目是怎么一步一步走到现在的
- 哪些判断已经有证据支撑
- 为什么当前主线是现在这个样子
- 后续协作者继续工作时，应该沿着什么方法推进

## 一、项目真实目标
项目真正目标从来都不是“让电台随便发出一点像数字模式的信号”，而是同时满足这三件事：

1. **FT4 能真正进入数字发射链**
2. **发出的信号是合格、可被正常解码的 FT4**
3. **数字模式下仍然可以外部控频**

这三个目标的优先顺序不是固定不变的，而是随着证据变化不断调整。  
当前顺序已经收敛成：

1. 先保证 **合格 FT4**
2. 再把 **改频** 接回去

原因很简单：如果信号本身就不是合格 FT4，那么“能改频”没有意义。

## 二、我们为什么没有继续走公开源码重编译路线
项目早期做过一条基于公开 `uvk5cec-0.3q` 源码树的路线，但后来被证据否掉了。  
原因是：

- 实机刷入后菜单结构不对
- 没有真实数字模式入口
- 显示和行为都更像公开的早期源码基线，而不是你手上的真实 `0.3q`

后面进一步从作者发布页和实机结果确认：

- 公开源码树并不等于真实、可工作的数字模式 `0.3q` 成品固件
- 所以后续主线必须改成：
  - **真实 `0.3q` 二进制逆向**
  - **真实 `UVK5DigManager.exe` 二进制逆向**

这也是为什么当前仓库的核心不是“重编译源码”，而是：

- 解包真实固件
- 生成 patch manifest
- 打补丁
- 重新打包

## 三、我们当前采用的研发方法
当前方法可以概括成一句话：

**用最小证据闭环驱动路线切换，而不是靠先验猜测。**

具体做法分 4 层：

### 1. 先抓“真实行为”
优先相信真实设备、真实程序和真实抓包，而不是文档印象。

我们用过的真实输入包括：

- 真实 `cec_0.3QB.packed.bin`
- 真实 `UVK5DigManager.exe`
- `FT4` / `FT8` 的真实 `5957` replay 样本
- 实机发射结果
- 第二接收机 / 第二套 `WSJT-X` 的客观表现

### 2. 先做窄目标逆向，不做大范围还原
我们没有把目标定成“还原完整源码”，而是定成：

- 找数字模式入口
- 找改频入口
- 找 `FT4` 为什么不起发射
- 找现在为什么起发射了但节拍不对

这样做的好处是：

- 每一轮都能快速产出一个可验证假设
- 不会因为“想彻底理解全部系统”而停在静态分析里

### 3. 先找最小可控改动，再做组合验证
当前所有主线补丁都遵循：

- 先做最窄补丁
- 先让功能往前走一步
- 再看新的实机结果改变了什么

例如：

- `patched DigiManager` 的第一步，不是重写程序，而是让 `protocol 4` 能通过原有 `protocol 8` 的数字下发门
- 固件补丁第一步，不是重写数字模式，而是尝试放开数字模式里的 retune 限制

### 4. 失败后必须做单端对照组
项目里很重要的一条方法论是：

**组合补丁失败时，不能只继续刷组合件，必须马上切单端对照。**

固定对照组是：

- `patched 固件 + 原版 DigiManager`
- `原版固件 + patched DigiManager`

这样做的目的，是快速把责任缩到：

- PC 侧
- 固件侧
- 还是双端交互

## 四、主线是怎么一步步改出来的
下面是到目前为止最关键的路线变化。

### 阶段 1：怀疑 FT4 根本没有进入发射链
早期实机结果是：

- `FT8` 能发
- `FT4` 不能发

那时主判断是：`FT4` 可能被挡在 `DigiManager` 或固件之前。

### 阶段 2：抓到 FT4 已经到达 DigiManager 的输入侧
通过 UDP 抓包和 replay 对照，确认：

- `FT4` 与 `FT8` 都已经能到 `5957`
- 只是行为不同

这一步把问题从“WSJT-X 没发”推进成了“DigiManager / 固件链没有正确处理 FT4”。

### 阶段 3：静态逆向显示 FT4 第一门控更像在 DigiManager 侧
对 `UVK5DigManager.exe` 做了 .NET 静态分析后，看到：

- `protocol 8` 能进入已有数字数据下发路径
- `protocol 244` 仍保留 retune 下发能力
- `protocol 4` 没有像 `8` 那样被真正 forward

这一步直接改变了路线：

- 不再坚持“只改固件”
- 改成 **DigiManager + 固件双端补丁**

### 阶段 4：新 DigiManager 已经让 FT4 起发射
实机最新结果表明：

- 只要用了新的 `patched DigiManager`
- 无论原版固件还是 patched 固件
- `FT4` 都已经能起发射

这条证据非常关键，因为它说明：

- `FT4` 起发射的第一门控，确实大概率在 DigiManager 侧
- 固件 retune 补丁不是“让 FT4 起发射”的第一责任点

### 阶段 5：现在的新主问题是“FT4 发出来了，但节拍不对”
目前最重要的新事实是：

- `FT4` 已经不是“不发”
- 而是“发出来的节拍明显慢于标准 FT4”

这就把主目标改成了：

- **先做固定频点下的合格 FT4**
- 再接回改频

## 五、我们当前已经能确定的事
截至现在，可以比较有把握地说：

1. 真实 `0.3q` 固件可以稳定解包、补丁、重打包
2. `patched DigiManager` 可以稳定生成
3. `FT4` 已经能起发射
4. `protocol 244` 的 retune 能力在 DigiManager 侧确实存在
5. 当前“慢节拍”现象同时出现在：
   - `patched DigiManager + 原版固件`
   - `patched DigiManager + patched 固件`

这一点意味着：

- 第一嫌疑对象现在是 **DigiManager 发送节拍**
- 而不是先把问题重新全部压回固件

## 六、我们当前还不能下死结论的事
截至现在，还不能当成已证明事实的包括：

1. 固件 retune 补丁已经完全放开数字模式改频
2. 当前 patched 固件一定不会影响 FT4 合规时序
3. 现在发出来的 FT4 已经符合规范
4. 当前组合路线已经能用于真正的卫星测试

所以当前所有候选件的定位仍然是：

- **受控台架测试件**
- **不是成品**

## 七、当前正确的实验顺序
这是协作者最应该遵守的一条：

### 第一步：固定频点下验证合格 FT4
优先用：

- `patched DigiManager + 原版固件`

主验收标准不是瀑布图，而是：

- 第二接收机 / 第二套 `WSJT-X` 是否能正常解码

### 第二步：只有固定频点 FT4 合格后，才测改频
切到：

- `patched DigiManager + patched 固件`

再测：

- 数字模式空闲态改频
- 数字模式发射态改频
- 同时看 `FT4` 是否仍可被正常解码

### 第三步：如果失败，立刻切单端对照
失败时必须继续做：

- `patched 固件 + 原版 DigiManager`
- `原版固件 + patched DigiManager`

不要只重复刷组合件。

## 九、协作者继续推进时的决策原则
后续如果你要继续往前推进，请优先遵守这几条：

1. **先保合规，再谈改频**
   - 只要 `FT4` 还不能被第二接收机正常解码，就不要先把“改频是否生效”当主问题

2. **优先做最窄改动**
   - 不要为了一个验证点一次性重写大块逻辑

3. **每轮只解决一个主要矛盾**
   - 现在主要矛盾是 `FT4` 时序是否合规
   - 不是卫星联动
   - 不是 UI 体验
   - 不是量产发布

4. **每次实机测试都要可追溯**
   - 使用了哪份固件
   - 使用了哪份 DigiManager
   - 第二接收机是否解码成功
   - 是否启用了诊断版

5. **失败后必须做对照组**
   - 不允许只凭一次失败就修改主判断

## 十、目前最合理的下一步
当前最合理的下一步不是继续加更多功能，而是：

1. 用 `patched DigiManager + 原版固件`
2. 验证固定频点下 `FT4` 是否已经能被第二接收机正常解码
3. 如果仍然明显慢于标准 `FT4`
   - 优先继续修 `DigiManager` 发送节拍
4. 只有这一步通过后
   - 才继续把 patched 固件和 retune 接回去

## 十一、一句话总结
这个项目到现在的研发方法，可以概括成一句话：

**先用真实证据缩小责任层，再用最窄补丁推进一小步，并用单端对照组防止把错误归因放大。**
